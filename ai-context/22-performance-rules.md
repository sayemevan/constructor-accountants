# 22 — Performance Rules

Load when: writing list/report queries, adding indexes, handling images, exports, dashboards, or large tables.

## Budgets (production, p95)
List/detail API < 300 ms · dashboard < 800 ms · report up to 1 year of data for one project < 2 s (otherwise async
export) · attendance bulk save for 100 workers < 1 s · first contentful paint on 4G mobile < 2.5 s ·
JS for a typical route < 250 KB gzipped.

## Database
- Every query on a tenant-owned table filters by `tenant_id` first; indexes lead with `tenant_id`.
- Index what you filter/sort by: see 05 for baseline indexes. Add an index with the query it serves noted in the
  migration comment. Check plans with `EXPLAIN (ANALYZE, BUFFERS)` on realistic data for new heavy queries.
- No unbounded queries: every list is paginated (max 100); every report is bounded by date range and tenant.
- Avoid N+1: batch-load related data (`where: { id: { in: ids } }`), use `select` to fetch only needed columns.
- Aggregations (sums, group by) happen **in SQL**, never by loading rows into Node.
- Keep transactions short; no external calls inside; lock rows in a consistent order (by id) to avoid deadlocks.
- Use `includeTotal=false`/cursor pagination for large append-only feeds (audit, notifications).
- Connection pool sized per instance (e.g., 10) × replicas < DB max connections; PgBouncer (transaction mode) when
  replica count grows.
- Seed a **performance dataset** (e.g., 1 tenant × 50 projects × 200k transactions × 1M attendance rows) for
  query testing before release.

## Reports & dashboards
- MVP: computed live from source tables with proper indexes.
- When a report exceeds budgets: first optimize query/indexes; then add a **summary table** maintained by the
  owning module in the same transaction or by an outbox handler (e.g., `project_financial_summaries`), with a
  nightly verification job. Materialized views are acceptable for tenant-wide dashboards refreshed by job.
- Large exports (> 5k rows or > 2 s) run as background jobs producing a file (15) — streaming writes, not in-memory.
- Dashboard endpoints return pre-aggregated small payloads; no client-side aggregation over raw lists.

## Caching
- Browser: TanStack Query with sensible `staleTime` (lists 30 s, reference data like categories/roles 5 min),
  invalidate on mutation.
- Server: per-request memoization of session/permissions. Cross-request caches (Redis) only with measured need,
  keys always include tenantId, and invalidation defined.
- HTTP caching: static assets immutable with hashed names; API responses `Cache-Control: no-store` for
  authenticated data.

## Files & images
- Client-side resize/compress photos before upload; direct-to-storage uploads (no proxying bytes through API for S3).
- Thumbnails generated by worker; lists show thumbnails only; lazy-load images (`loading="lazy"`), fixed aspect
  boxes to avoid layout shift.
- Batch-issue signed URLs per page.

## Background processing
Anything > 1 s or retry-worthy (email, exports, thumbnails, scans, reminder scans) goes to a job. Jobs are chunked
(e.g., 500 rows per batch) and resumable. Per-tenant jobs to avoid one large tenant starving others; queue
concurrency limits per job type.

## Frontend rendering
- Route-level code splitting; lazy-load charts, rich editors, and heavy dialogs.
- Server-side pagination for tables; virtualize only when a view must show > 200 rows at once (e.g., attendance
  grid for large crews).
- Debounce search inputs (300 ms); avoid refetch storms (precise query keys).
- Memoize expensive derived UI data; avoid re-rendering whole tables on single-row edits.
- Measure with Lighthouse (mobile profile) on key pages before release.

## Growth checkpoints (revisit when crossed)
10k tenants or 100M transaction rows → evaluate partitioning, read replica for reporting, summary tables for all
dashboard metrics. Anything beyond → ADR before adding infrastructure.
